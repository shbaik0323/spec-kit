# 역사

Spec Kit은 명세를 AI 지원 개발의 출발점으로 삼기 위한 툴킷으로 시작했습니다.
[첫 번째 전체 체크인](https://github.com/github/spec-kit/commit/28fdfaa86973d4402eecd89ba6c87d31e1edae03)부터
스펙 주도 개발을 적용하는 세 가지 방식을 설명했습니다.

- **0에서 1로의 개발("그린필드")**은 요구사항으로부터 새 시스템을 생성합니다.
- **창의적 탐색**은 병렬 구현, 기술 선택, 경험 설계를 비교합니다.
- **반복적 개선("브라운필드")**은 기존 시스템에 기능을 추가하고 현대화합니다.

세 가지 모두 지속되는 계획 아티팩트에서 구현으로 나아갔습니다.

**Specify → Plan → Tasks → Implement**

이 개발 경로와 핵심 순서는 그대로 남아 있지만, 프로젝트는 코딩 에이전트, 소프트웨어
전달 프로세스, 그 밖의 구조화된 작업을 위한 확장 가능한 하네스로 성장했습니다.

## 프로젝트 관리 주체

Spec Kit의 역사에는 뚜렷이 구분되는 두 번의 관리 시기가 있습니다. 여기에 이를
기록하는 것은 이 작업을 어느 한 사람의 것으로 축소하지 않으면서 프로젝트
리더십에 대한 당대의 기록을 보존하기 위함입니다.

### 창립기 관리: 2025년 8월–2026년 1월

[Den Delimarsky](https://github.com/localden)와
[John Lam](https://github.com/jflam)이 Spec Kit을 구상하고 프로젝트에 처음 형태를
부여했습니다. Den은 2025년 8월 21일에
[최초 커밋](https://github.com/github/spec-kit/commit/fa2736371e077f55c4fe145fea186bab2561386d)을
작성했고 첫 몇 달 동안 저장소를 이끌었습니다.

이 창립기에 사용자들이 지금도 알아보는 형태가 자리 잡았습니다. Specify CLI, 코딩
에이전트별 스캐폴딩, 프로젝트 컨스티튜션, 그리고 명세 → 계획 → 태스크 → 구현
프로세스입니다. 또한 SDD를 단일 에이전트나 개발 시나리오에 묶지 않고 그린필드
개발, 병렬 탐색, 브라운필드 개선에 유용한 방법으로 규정했습니다.

### 커뮤니티 관리: 2026년 1월–현재

[Manfred Riem](https://github.com/mnriem)이 2026년 1월 22일에 리드 메인테이너를
맡았습니다. 이 전환은 2월 23일에 저장소의 전역
[`CODEOWNERS` 항목](https://github.com/github/spec-kit/commit/3040d33c31d8a26d50f91aec5d62d1cecac3298c)이
`@mnriem`으로 바뀌면서 공개적으로 드러났습니다.

이 관리 시기 동안 메인테이너 팀의 초점은 합성 가능한 모델을 만드는 것에서 그
모델을 사용해 완전한 퍼스트파티 프로세스를 출시하는 것으로 옮겨 갔습니다.
커뮤니티에게 이 변화는 순차적이지 않았습니다. 모듈식 확장 시스템은 커뮤니티
기여로 시작되었고, 기여자들은 각 프리미티브가 도착하는 대로 채택하고 확장했습니다.

이 날짜와 역할은 리드 메인테이너의
[6개월 회고](https://www.manorrock.com/blog/2026/07/22/six_months_leading_spec_kit.html)와
[1주년 기록](https://www.manorrock.com/blog/2026/08/21/spec_kit_turns_one.html)에도
문서화되어 있으며, 저장소의 커밋 및 소유권 이력과 일치합니다.

## 마일스톤

### 2025년 8월: 기반

저장소 이력은 2025년 8월 21일에 시작됩니다. 첫 릴리스들이 Specify CLI, 재사용
가능한 템플릿, 핵심 스펙 주도 개발 경로를 확립했습니다. 중앙에서 설정되는
에이전트별 스캐폴딩을 통한 여러 코딩 에이전트 지원은 처음부터 프로젝트의
일부였으며, 프로세스를 특정 모델이나 도구로부터 독립적으로 유지했습니다.

### 2026년 2월–4월: 프리미티브 구축

모듈식 확장 시스템은 2월에 Michal Bachorik의 커뮤니티 기여로 도입되어, 핵심
프로세스를 늘리지 않고도 기능을 추가할 수 있게 했습니다. 3월에는 플러그형 프리셋이
도입되어 같은 CLI 경험을 유지하면서 템플릿과 명령을 교체하거나 합성할 수 있게
되었습니다.

창립기의 에이전트 스캐폴딩은 레지스트리 기반 통합 아키텍처로 다시 작성되었습니다.
코어 자산도 Python 패키지에 내장되어 오프라인 및 에어갭 환경에서 안정적으로
초기화할 수 있게 되었습니다.

4월에는 워크플로 엔진이 카탈로그로 배포되는 자동화와 내장 워크플로 스텝 타입을
도입했습니다. 워크플로는 사용자가 모든 명령을 수동으로 호출하도록 요구하는 대신
재사용 가능한 스텝을 조율할 수 있게 되었습니다. 이어서 통합 카탈로그가 나와 코딩
에이전트 지원을 탐색하고 독립적으로 배포할 수 있게 되었습니다.

합성 가능한 모델은 다섯 가지 프리미티브로 설명되기에 이르렀습니다.

- **통합**은 Spec Kit을 코딩 에이전트에 연결합니다.
- **확장**은 기능, 명령, 템플릿, 스크립트, 훅을 추가합니다.
- **프리셋**은 동작을 사용자 정의하거나 대체합니다.
- **워크플로**는 여러 단계로 이루어진 프로세스를 자동화합니다.
- **워크플로 스텝**은 워크플로 동작의 재사용 가능한 단위를 제공합니다.

이 첫 몇 달 동안의 강조점은 재사용 가능한 장치를 만드는 데 있었습니다. 더 많은
퍼스트파티 프로세스를 추가하기 전에 프로세스를 설정 가능하고, 배포 가능하고,
자동화 가능하게 만드는 것이었습니다. 커뮤니티 기여자들은 전체 모델이 완성되기를
기다리지 않았습니다. 새로운 확장 및 프리셋 표면을 재빨리 활용해 자신만의 기능과
프로세스 변형을 게시했습니다.

### 2026년 6월–7월: 프리미티브의 합성과 적용

코어 팀에게 6월은 주로 프리미티브를 만들던 단계에서 그것을 사용하는 단계로 넘어가는
전환점이었습니다. 워크플로 스텝 카탈로그가 사용자 정의 스텝 타입을 커뮤니티에서
설치할 수 있게 만들어, 4월에 워크플로 엔진과 함께 출시된 프리미티브를 확장했습니다.
이어서 번들이 확장, 프리셋, 워크플로, 스텝을 역할이나 팀을 위한 일관된 구성으로
패키징할 수 있게 했으며, 선택적으로 특정 통합을 대상으로 지정할 수 있습니다.

카탈로그는 프리미티브와 커뮤니티를 잇는 다리가 되었습니다. 커뮤니티 작성자들은
확장, 프리셋, 통합, 워크플로, 스텝 타입, 번들을 만들었고, 메인테이너 팀은 제출
메타데이터를 확인하고 수락된 항목을 커뮤니티 카탈로그에 등재해 사용자가 탐색하고
설치할 수 있게 했습니다. 카탈로그 등재는 컴포넌트를 보이게 했을 뿐, 그 코드가
감사를 받았거나 보증되었다는 뜻은 아니었습니다.

동시에 코어 메인테이너들은 이 모델을 사용해 기능 전달과 나란히 두 개의 퍼스트파티
프로세스를 추가하기 시작했습니다.

- 6월 5일, 버전 0.9.5가 번들로 제공되는 선택형
  [`bug` 확장](https://github.com/github/spec-kit/commit/60302fefec541a68fcac6f0428a95ba35f2acadf)을
  도입했습니다. 이 확장의 평가 → 수정 → 테스트 프로세스는 버그 진단, 교정, 검증을
  분리하고 문서화된 상태로 유지합니다.
- 7월 17일, 버전 0.13.0이 번들로 제공되는 선택형
  [`assess` 확장](https://github.com/github/spec-kit/commit/208d38695fc88d8eaec7855c96e5098a852927cf)을
  도입했습니다. 이 확장의 접수 → 조사 → 정의 → 구체화 → 결정 프로세스는 아이디어가
  SDD에 들어가기 전에 평가합니다.

6월에는 `/speckit.converge`로 핵심 전달 루프도 닫혔습니다. 구현을 종착점으로
취급하는 대신, 코드를 명세·계획·태스크에 비추어 평가한 다음 남은 누락에 대해 추적
가능한 태스크를 추가합니다. 이 태스크들은 `/speckit.implement`로 돌아가, 명세나
계획을 다시 쓰지 않고도 수렴 루프를 만듭니다.
[6월 뉴스레터](https://github.com/github/spec-kit/blob/main/newsletters/2026-June.md)는
구현을 생성하는 것에서 그것이 기록된 의도를 충족하는지 확인하는 것으로의 이
전환을 기록합니다.

7월에는 [에이전트 네이티브 런타임 이벤트](../integrations/cli.md#runtime-events)가
추가되어, 확장이 세션 시작이나 도구 사용 같은 코딩 에이전트 라이프사이클 이벤트에
반응할 수 있게 되었습니다. 명령 훅과 달리 이 이벤트들은 에이전트에게 추가 지침을
따르라고 요청하는 대신 스크립트를 직접 실행합니다. 이제 통합은 명령이나 스킬을
전달하는 데 그치지 않고 Spec Kit 동작을 에이전트의 런타임에 연결할 수 있게
되었습니다.

배포 경로도 넓어졌습니다. 릴리스 파이프라인에 PyPI 게시가 추가되었고, Python이
Bash와 PowerShell에 이어 지원되는 프로젝트 스크립트 유형으로 합류했습니다. 이
변화들은 오프라인 및 엔터프라이즈 환경 지원을 유지하면서 설치와 크로스 플랫폼
사용을 더 단순하게 만들었습니다.

### 2026년 8월: 1주년

Spec Kit은 2026년 8월 21일에 한 돌을 맞아 버전 1.0.0을 릴리스했습니다. 그 무렵
다섯 가지 프리미티브, 즉 통합, 확장, 프리셋, 워크플로, 워크플로 스텝은 이미 일관된
모델을 이루고 있었습니다. 번들은 선택된 통합을 중심으로 확장, 프리셋, 워크플로,
스텝을 합성했습니다. README 개편으로 기존의 SDD, 버그 수정, 아이디어 평가
프로세스를 별도의 빠른 시작 문서를 통해 더 쉽게 찾을 수 있게 되었습니다.

버전 1.0.0은 그 모델을 만들어 내거나 동결하지 않았습니다. 프로젝트의 진화하는
상태에 딱 떨어지는 숫자를 붙였을 뿐입니다. 당시 문서는 38개의 코딩 에이전트 통합,
157개의 커뮤니티 확장, 33개의 프리셋, 270명 이상의 기여자를 보고했습니다. Spec
Kit은 계속해서 적응성을 중시합니다. 프로세스, 통합, 관례는 진화할 수 있고,
에이전트는 프로젝트가 그런 변화를 적용하도록 돕습니다.

[1.0.0 릴리스](https://github.com/github/spec-kit/releases/tag/v1.0.0)는
프로젝트가 완성되었다거나 형태가 동결되었다는 약속이 아니라 1년간의 작업을
기념했습니다. 리드 메인테이너의 개인적인 1주년 글
[*Spec Kit Turns One — and Ships 1.0.0*](https://www.manorrock.com/blog/2026/08/21/spec_kit_turns_one.html)에서
1.0.0은 **이제 그저 숫자일 뿐**입니다. 에이전트가 변화에 적응하는 비용을 낮추면서
가치는 안정성에서 적응성으로 옮겨 갑니다.

1주년은 Spec Kit을 사용하고, 그 가정에 이의를 제기하고, 문제를 보고하고, 코드나
문서를 기여하고, 확장이나 프리셋을 만들고, 아이디어를 나누고, 누군가의 시작을 도운
모든 사람을 기리는 자리이기도 했습니다. 이 마일스톤은 프로젝트를 첫 해 동안 이끌어
왔고 지금도 계속 만들어 가고 있는 커뮤니티의 것입니다.

8월에는 통합 및 프로세스 모델이 일상적인 사용에서도 더 구체화되었습니다. Copilot
초기화가 기본적으로 스킬을 사용하도록 전환되어, 레거시 마크다운 명령 레이아웃을
대체하는 기본 전달 경로가 되었습니다. 프로젝트는 Spec Kit을 초기화하고 `assess`
확장을 실행하는 `feature-assess` 에이전트 기반 워크플로를 통해, 들어오는 기능
요청에 자체 아이디어 평가 프로세스를 적용하기 시작했습니다.
[8월 뉴스레터](https://github.com/github/spec-kit/blob/main/newsletters/2026-August.md)는
에이전트 네이티브 전달 변경과 Spec Kit 자체의 유지 관리를 돕는 데 Spec Kit을
사용한 일을 모두 기록합니다.

### 2026년 9월: 들여다볼 수 있는 합성

9월에는 합성 가능한 모델이 더 세밀해지고 조회하기 쉬워졌습니다. 프리셋에는
명시적인 확장 의존성이, 워크플로에는 재사용 가능한 삽입 지점을 위한 이름 있는
슬롯이 생겼고, 개별 스텝이 자체 통합 설정을 가질 수 있게 되었습니다. 새로운
[`specify artifact` 명령 그룹](artifacts.md)은 명령, 템플릿, 스크립트, 훅을 합성
스택 및 기여 레이어와 함께 JSON으로 노출했습니다. 도구와 에이전트는 설정만으로
추론하는 대신 프로젝트에 설치된 레이어가 실제로 무엇을 만들어 냈는지 조회할 수
있게 되었습니다.

생태계는 확장 모델이 일반적인 개발 안내를 넘어서는 구체적인 사례도 제공했습니다.
9월에 Microsoft의 Azure Cosmos DB 팀이 공개 미리 보기로
[Spec Kit용 최초의 데이터베이스 확장을 발표](https://devblogs.microsoft.com/cosmosdb/spec-driven-development-comes-to-azure-cosmos-db-the-first-database-extension-for-github-spec-kit/)해,
데이터베이스에 특화된 안내를 구현 프로세스에 들여왔습니다. 이는 Spec Kit
메인테이너와는 별개인 Microsoft 제품 팀의 작업이었으며, 독립적인 서드파티 채택은
아니었습니다. 이와 함께 커뮤니티 작성자들은 자신들의 컴포넌트로 카탈로그를 계속
확장했습니다.
[9월 뉴스레터](https://github.com/github/spec-kit/blob/main/newsletters/2026-September.md)는
합성 관련 변경과 생태계 성장을 모두 기록합니다.

### 2026년 10월–11월: 프로그래밍 방식 접근과 더 깊은 합성

10월에는 실험적인 로컬
[Model Context Protocol(MCP) 서버](mcp.md)가 도입되어, 처음에는 버전 정보를,
이후에는 아티팩트 조회와 설치된 워크플로 목록을 노출했습니다. 이 읽기 전용 도구들은
MCP 클라이언트가 Spec Kit을 직접 조회할 수 있게 했습니다. 설치, 변경, 워크플로
실행은 노출하지 않았습니다. CLI와 일급 MCP 도구는 공유 작업으로 디스패치하므로,
같은 동작의 별도 구현을 만들지 않고 접근을 확장합니다.

합성도 더 많은 경계를 넘어 확장되었습니다. 코딩 에이전트 어댑터를
[카탈로그에서 설치할 수 있게](../integrations/cli.md#catalog-installed-external-adapters)
되어, 사용자의 명시적인 신뢰 결정을 전제로 에이전트별 지원을 코어 패키지 밖에서
배포할 수 있게 되었습니다. 워크플로에는 통합된 실행 트리 안에서
[다른 워크플로를 호출](../workflow-steps/types.md#workflow-composition)하는 기능이,
번들에는 [다른 번들에 대한 참조](../bundles/api.md#bundle-references)가
생겼습니다. 11월 초에는 실행 범위 워크플로 정의도 `specify workflow definition`으로
조회할 수 있게 되었습니다. 이 변화들이 함께 새로운 개발 프로세스를 도입하지 않고도
기존 프리미티브를 더 재사용 가능하게, 그 유효 설정을 더 잘 보이게 만들었습니다.

## 변하지 않는 주제

몇 가지 주제가 프로젝트의 관리 시기와 기술적 진화를 관통합니다.

- **의도가 구현보다 먼저입니다.** 명세는 기술적 결정이 작업을 지배하기 전에
  무엇을 만들어야 하는지 포착합니다.
- **아티팩트는 지속되어야 합니다.** 스펙, 계획, 태스크는 단일 프롬프트나 에이전트
  세션을 넘어 계속 유용합니다.
- **프로세스는 에이전트에 독립적이어야 합니다.** 팀은 개발 방법을 버리지 않고도
  코딩 에이전트를 바꿀 수 있습니다.
- **방법은 작업에 맞춰져야 합니다.** 원래의 개발 경로는 팀이 수정, 자동화, 대체할
  수 있는 공식적으로 합성 가능한 모델로 성장했습니다.
- **커뮤니티가 키트를 만들어 갑니다.** 커뮤니티 기여는 프로젝트의 인프라와 그 위에
  세워진 생태계 모두에 영향을 미쳤습니다.

## 릴리스 이력

기록합니다. 릴리스 수준의 세부 사항은
[변경 로그](https://github.com/github/spec-kit/blob/main/CHANGELOG.md)와
