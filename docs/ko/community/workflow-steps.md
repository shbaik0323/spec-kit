# 커뮤니티 워크플로 스텝 타입

> [!NOTE]
> 커뮤니티 워크플로 스텝 타입은 각 작성자가 독립적으로 만들고 유지 관리합니다.
> 메인테이너는 제출 메타데이터와 패키지 형태를 확인할 뿐, **실행 가능한 Python
> 코드를 검토, 감사, 보증, 지원하지 않습니다**.
> 설치는 Python 코드를 임포트하지 않고 패키지를 검증하고 복사합니다. 이후의
> `specify workflow add`, `run`, `resume` 명령은 설치된 스텝 패키지를 로드하며,
> 임포트 시점 코드를 사용자의 권한으로 실행합니다. 설치하고 사용하기 전에 소스를
> 검토하세요.

사용자 정의 워크플로 스텝 패키지는 내장 스텝 타입을 넘어 워크플로가 사용할 수 있는
`type:`을 추가합니다. 정식 접수 경로는 새 항목, 버전 업데이트, 메타데이터 수정을
위한
[Workflow Step Type Submission](https://github.com/github/spec-kit/issues/new?template=workflow_step_submission.yml)
이슈 양식입니다.

양식을 열면 `triage-must-have` 판정만 적용됩니다. 메인테이너가 분류 중에
`workflow-step-submission`을 적용해 자동화된 메타데이터 검증을 시작합니다. 검증이
성공하면 메인테이너 리뷰를 위한 초안 PR로 카탈로그 및 문서 변경이 제안됩니다.
자동화는 제출된 Python을 설치, 임포트, 실행, 검토하지 않습니다.

수락된 항목은
[`workflows/step-catalog.community.json`](https://github.com/github/spec-kit/blob/main/workflows/step-catalog.community.json)에
게시됩니다. 내장 커뮤니티 카탈로그는 **탐색 전용**입니다. 수락된 항목은
`specify workflow step search`와 `info`에 나타날 수 있지만,
`specify workflow step add <id>`는 그 소스로부터 실행 코드를 설치하지 않습니다.
소스를 검토한 뒤, 제출된 버전 지정 아카이브를 `--from`으로 직접 설치하거나, 설치를
명시적으로 허용하도록 별도로 설정한 스텝 카탈로그를 사용하세요.

## 사용 가능한 스텝 타입

| 스텝 타입 | 버전 | 설명 |
| --- | --- | --- |
| [Decision](https://github.com/markuswondrak/spec-kit-decision-step) (`decision`) | 0.9.0 | Jev 및 Laya 백엔드를 사용해 네이티브 확률과 점수 범례를 갖춘, 타입이 있는 제한된 선택·점수·noul 결정을 내립니다. |

Decision은 [Markus Wondrak](https://github.com/markuswondrak)이 유지 관리합니다.
다른 커뮤니티 제출 표와 마찬가지로 작성자 메타데이터는 카탈로그에 속하며,
메인테이너 귀속을 대신하는 데 쓰이지 않습니다.

Decision은 Spec Kit `>=0.11.0`과의 런타임 호환성을 선언합니다.
[버전 지정 릴리스 아카이브](https://github.com/markuswondrak/spec-kit-decision-step/releases/download/v0.9.0/decision-0.9.0.zip)를
`--from`으로 설치하려면 Spec Kit `>=1.1.0`이 필요합니다. 카탈로그의 호환성 필드는
권고 사항이며 현재 스텝 설치 프로그램이 강제하지 않습니다.

이 패키지는 호스트의 PyYAML과 `specify_cli` 패키지를 사용합니다. Jev에는
`TYPESAFE_API_KEY`(또는 설정된 `api_key_env`)와 설정된 백엔드 엔드포인트로의
아웃바운드 HTTPS가 필요하고, 프로세스 내 Laya에는 선택적인 `laya[onnx]` 패키지가
필요합니다. 설정, 출력, 실패 동작, 부수 효과는
[버전 고정 문서](https://github.com/markuswondrak/spec-kit-decision-step/blob/v0.9.0/README.md)를,
릴리스 세부 사항은
[변경 로그](https://github.com/markuswondrak/spec-kit-decision-step/blob/v0.9.0/CHANGELOG.md)를
참고하세요. MIT 라이선스 매니페스트는 패키지 작성자로
`spec-kit-decision-step contributors`를 명시합니다.

## 패키지 계약

설치된 패키지 하나가 워크플로 스텝 타입 하나를 제공합니다.

```text
my-step/
├── step.yml
├── __init__.py
└── helpers.py     # optional; every catalog-downloaded extra file is declared
```

패키지는 현재 설치 프로그램 및 로더 계약을 충족해야 합니다.

- `step.yml`과 `__init__.py`는 패키지 루트에 있는, 심볼릭 링크가 아닌 일반
  파일입니다. 아카이브는 패키지를 정확히 하나의 최상위 디렉터리로 감쌀 수
  있습니다.
- `step.type_key`, 카탈로그 키/ID, 그리고 일치하는 `StepBase.type_key`가
  동일합니다.
- ID는 하나의 안전한 경로 구성 요소입니다. 설치 프로그램은 구분자, 맨 앞의 점, 끝의
  점이나 공백, 예약된 이름, 제어 문자, Windows에서 유효하지 않은 파일명 문자를
  거부합니다. 카탈로그 자동화는 추가로 문자로 시작하는 소문자, 숫자, 하이픈을
  요구합니다.
- `__init__.py`는 그 단일 타입 키와 일치하는 `StepBase` 하위 클래스를 정의합니다.
  클래스를 더 둔다고 해서 패키지가 추가로 등록된 스텝 타입을 제공하지는 않습니다.
  이는 메인테이너의 코드 확인이 아니라 작성자의 확인 사항입니다.
- 추가 파일 경로는 슬래시를 사용하고, 상대 경로이며 비어 있지 않고, 빈 세그먼트나
  `.`·`..` 세그먼트가 없으며, 대소문자를 무시했을 때 `step.yml`, `__init__.py`,
  다른 파일, 패키지 디렉터리와 겹치지 않습니다.
- 패키지는 현재 설치 프로그램의 한도 안에 머뭅니다. 유지 항목 512개(파일과
  디렉터리 합산), 디렉터리 32단계, 유지 콘텐츠 50 MiB입니다. 제출 다운로드에는
  추가로 파일당 10 MiB 한도가 있습니다.
- `.git`, `__pycache__`, `.DS_Store`는 설치에서 제외됩니다. 제출 자동화는 이
  구성 요소의 대소문자 무시 별칭을 거부합니다.

패키지 검증과 런타임 동작은
[사용자 정의 스텝 패키지](../workflow-steps/developing.md#custom-step-packages)를,
설치는 [스텝 설치 레퍼런스](../workflow-steps/cli.md#step-management)를
참고하세요.

## 제출 계약

이슈 양식은 현재 패키지/카탈로그 코드가 사용하는 필드와 메타데이터 검토 중에
사용하는 출처 및 공개 필드를 구분합니다.

| 제출 데이터 | 현재 계약 |
| --- | --- |
| 스텝 타입 ID | 카탈로그 키, `step.type_key`, 일치하는 `StepBase.type_key` |
| 이름, 버전, 설명, 작성자 | `step.yml` 메타데이터와 카탈로그/설치 레지스트리 메타데이터 |
| Download URL | 지원되는 직접 URL 설치 경로를 테스트하는 데 쓰이는 버전 지정 릴리스 아카이브 |
| `step.yml`, `__init__.py`, 추가 파일 URL | 명시적으로 설치가 허용된 카탈로그에서 설치할 때 사용되는 정확한 HTTPS 파일 URL. 추가 파일 키는 위의 패키지 상대 경로 제한을 따름 |
| 파일별 SHA-256 매핑 | 카탈로그 `sha256`. 키는 설치 프로그램이 다운로드하는 파일과 정확히 일치해야 함 |
| 제공 타입 이름/수 | 로더 불변 조건: 설치된 패키지당 일치하는 타입 키 하나 |
| 저장소, 라이선스, 문서, 변경 로그 | 소스 출처와 메타데이터 검토 근거. `step.yml` 필드가 아님 |
| Spec Kit 호환성 | 필수 접수 공개 사항. 권고용 `requires.speckit_version`으로 저장되며 설치 프로그램이 강제하지 않음 |
| 런타임 및 도구 의존성 | 필수 접수 공개 사항. CLI는 사용자 정의 스텝의 의존성을 해석하거나 설치하지 않음 |

다른 커뮤니티 제출 양식과 일관되게 아카이브에는 버전이 지정된 GitHub 릴리스 URL을
사용하세요. 버전은 PEP 440과 호환되어야 하며 매니페스트와 일치해야 합니다.
아카이브의 릴리스 태그는 그 버전을 식별해야 하며, 선택적으로 `v` 접두사나 범위
접두사를 가질 수 있고, 슬래시가 없어야 합니다.
`1!2.0` 같은 epoch 버전과 `2.0+cpu` 같은 로컬 버전이 지원됩니다. 태그 문자는
`^[A-Za-z0-9._~+!-]+$`와 일치해야 합니다.
모든 카탈로그 파일 URL은 제출된 저장소의 `raw.githubusercontent.com`을 사용하고,
그 정확한 릴리스 태그와 패키지 디렉터리에 고정되어야 합니다. 필수인 파일별 SHA-256
매핑은 참조된 태그가 나중에 옮겨지더라도 바뀐 바이트를 감지합니다. 브랜치 URL,
`releases/latest` URL, 그 밖의 유동적인 대상을 제출하지 마세요.

아카이브 URL 경로는 `^[A-Za-z0-9._~+!/-]+$`와 일치해야 합니다. 패키지 상대 파일
키와 태그 안의 파일 경로는 `^[A-Za-z0-9._~/-]+$`와 일치해야 합니다.
공백, 퍼센트 이스케이프(자산 이름의 `%20` 포함), 쿼리 문자열, 프래그먼트, 비어
있거나 점이거나 경로 순회인 파일 경로 세그먼트는 커뮤니티 제출 자동화가 받아들이지
않습니다. 지원되지 않는 문자를 URL 인코딩하지 말고, 아카이브와 패키지 파일을 이
문자 집합 안의 이름으로 게시하세요.

GitHub가 생성하는 `archive/refs/tags/<tag>` 아카이브는 `.zip`과 `.tar.gz`만
지원합니다. `.tgz` 아카이브는 생성된 태그 아카이브가 아니라 이름이 있는
`releases/download/<tag>/<asset>.tgz` 릴리스 자산이어야 합니다.

문서는 제출된 GitHub 저장소의 태그에 고정된 어떤 Markdown 파일(`.md`, 대소문자
구분 없음)이든 될 수 있으며, `docs/deploy.md`도 가능합니다. `README.md`라는 이름일
필요는 없습니다. 설치, 설정, 의존성, 출력, 실패 동작, 부수 효과, 워크플로 사용
예시를 설명해야 합니다.

직접 `--from` 아카이브 설치 프로그램은 현재 아카이브 다이제스트를 받거나 검증하지
않습니다. 제출된 Download URL과 Testing Details 필드는 버전 지정 릴리스와 설치
테스트의 근거일 뿐, 불변 콘텐츠의 보장이 아닙니다. 파일별 다이제스트는 별도의
카탈로그 설치 경로를 보호합니다.
자동화는 누적 바이트 예산을 강제하기 위해 선언된 파일 전체를 한 번에
다운로드합니다. 아카이브나 그 내용을 실행하지 않습니다.

라이선스는 공식 라이선스 목록의 정확한 SPDX 라이선스 식별자 하나여야 하며, 제출된
릴리스 태그에서 감지된 저장소 라이선스와 일치해야 합니다.
알 수 없는 식별자나 알려진 라이선스 불일치는 검증을 실패시킵니다. 릴리스 라이선스
감지를 사용할 수 없거나 결론이 나지 않으면, 라이선스를 추측하는 대신 메인테이너의
확인을 위해 검증이 차단됨(Blocked) 상태가 됩니다. 이 메타데이터 확인은 법률 의견이나
코드 감사가 아닙니다.

## 제출 준비

1. 완전한 패키지, 라이선스, 문서, 그리고 해당하는 경우 변경 로그를 담은 공개 소스
   저장소를 만듭니다.
2. 유효한 설정과 유효하지 않은 설정, `StepStatus`, 출력, 오류, 그리고 관련 재개,
   중첩 스텝, 동시 실행 동작을 테스트합니다.
3. 버전 지정 릴리스 아카이브(`.zip`, `.tar.gz`, 또는 이름 있는 `.tgz` 릴리스
   자산)를 게시하고 테스트합니다.

   ```bash
   specify workflow step add my-step \
     --from https://github.com/your-org/my-step/releases/download/v1.0.0/my-step-1.0.0.zip
   ```

4. `step.yml`, `__init__.py`, 모든 추가 패키지 파일에 대해 태그에 고정된 원시 GitHub
   URL을 게시합니다. 다운로드한 각 파일의 SHA-256 다이제스트를 계산합니다.
5. 정확한 릴리스 메타데이터와 테스트 근거를 담아 정식 제출 이슈를 제출합니다.

## 자동화된 메타데이터 검증

메인테이너가 트리거하는 워크플로는 완전한 메타데이터, 일치하는 매니페스트 정체성,
고정된 릴리스/파일 URL, 파일별 다이제스트, 패키지 경로와 한도, 문서, 작성자의 테스트
확인 사항을 확인합니다. 제출된 코드를 검토하거나 그 실행 동작을 검증한다고 주장하지
않습니다.

확인된 제출 결함은 `validation-failed`와 조치 가능한 수정 사항을 만듭니다. 권한,
사용할 수 없는 도구, 타임아웃, 일시적인 HTTP 실패를 포함한 환경 실패는 제출 결함이
아니라 차단됨(Blocked)으로 처리됩니다. 보호된 결론 작업만이 초안 카탈로그 PR이
성공적으로 게시된 뒤 `validation-passed`를 적용할 수 있습니다.

새 버전은 기존 카탈로그 릴리스 이력을 보존합니다. 같은 버전의 메타데이터 수정은
명시적으로 밝혀야 하며 파일 URL이나 다이제스트를 교체할 수 없습니다. 패키지 내용이
바뀌면 새 버전을 게시하세요.
저장소가 소유한 검증기는 편집 전에 예상 카탈로그의 스냅샷을 만들고, PR 생성 전에
이전 현재 릴리스의 이전과 이력 보존을 포함해 생성된 카탈로그 전체를 확인합니다.
기존 릴리스 다이제스트가 없으면 메인테이너가 수리할 때까지 게시가 차단됩니다.
