# 번들 API 레퍼런스

이 페이지는 선언적 번들 매니페스트, 참조 확장, 설치 기록 계약을 정의합니다.
번들은 기존 컴포넌트를 합성하며, 별도의 실행 API를 제공하지 않습니다.

## 매니페스트

UTF-8 `bundle.yml` 파일은 YAML 매핑입니다. 번들 ZIP은 아카이브 루트에 이를 담아야
합니다. 완전한 예시는 개발 가이드에 있습니다.

| 필드 | 요구 사항 |
| --- | --- |
| `schema_version` | 필수. `"1.0"` 또는 `"1.1"` |
| `bundle` | 필수 메타데이터 매핑 |
| `requires.speckit_version` | 필수이며 비어 있지 않은 Spec Kit 버전 제약 |
| `requires.tools` | 선택적인 도구 이름 목록. 기본값은 빈 목록 |
| `requires.mcp` | 선택적인 MCP 서버 이름 목록. 기본값은 빈 목록 |
| `integration` | 비어 있지 않은 `id`를 가진 선택적 매핑 |
| `provides` | 선택적인 컴포넌트/참조 매핑 |
| `tags` | 선택적인 문자열 목록 |

없거나 null인 `requires`/`provides` 매핑은 빈 것으로 취급되지만, 필수인 Spec Kit
제약은 여전히 제공되어야 합니다. 존재하지만 매핑이 아닌 값은 유효하지 않습니다.
문자열 목록 필드는 단독 문자열일 수 없고 문자열이 아닌 멤버를 포함할 수 없습니다.

### 메타데이터

`bundle`의 모든 필드는 필수이며 비어 있지 않아야 합니다.

| 필드 | 의미 |
| --- | --- |
| `id` | 파일시스템에 안전한 번들 식별자 |
| `name` | 사람이 읽을 수 있는 이름 |
| `version` | 정확한 시맨틱 버전 |
| `role` | 대상 역할, 팀, 페르소나 |
| `description` | 구성에 대한 설명 |
| `author` | 작성자 또는 조직 |
| `license` | 라이선스 식별자 |

ID는 `^[a-z0-9](?:[a-z0-9._-]*[a-z0-9])?$`와 일치합니다. 소문자나 숫자로 시작하고
끝나며, 그 사이에 소문자, 숫자, 점, 밑줄, 하이픈이 올 수 있습니다. 경로 구분자와
경로 순회 ID는 유효하지 않습니다.

번들과 컴포넌트 버전은 완전한 `MAJOR.MINOR.PATCH` SemVer를 사용하며, 선택적으로
프리릴리스/빌드 메타데이터와 맨 앞의 `v` 또는 `V`를 붙일 수 있습니다. 컴포넌트
범위와 `latest`는 허용되지 않습니다. 반면 Spec Kit 요구 사항은
`">=0.9.0,<2.0.0"` 같은 제약입니다. 이는 설치/업데이트 중에 평가되며,
`bundle validate`가 실행 중인 버전에 대해 평가하지는 않습니다.

`requires.tools`와 `requires.mcp`는 요구 사항 경고를 만듭니다. 도구를 설치하거나,
MCP 서버를 프로비저닝하거나, 그 의존성이 있는지 검증하지 않습니다.

### 통합

```yaml
integration:
  id: copilot
```

`integration`을 생략하거나 null로 설정하면 번들은 통합에 중립적이 됩니다. 비어
있지 않은 ID가 없는 매핑은 유효하지 않습니다.

루트 번들은 프로젝트의 활성 통합과 일치해야 합니다. 통합을 전환하지는 않습니다.
참조된 번들의 통합 차이나 판별할 수 없는 유효 통합은 추가 통합 게이트가 아니라
경고입니다.

### 컴포넌트 참조

`provides.extensions`, `provides.presets`, `provides.steps`,
`provides.workflows`는 매핑의 목록입니다. 생략되었거나 null인 목록은 빈
목록입니다. 각 `(kind, id)`는 고정이 동일하더라도 매니페스트에 한 번만 나올 수
있습니다. 서로 다른 컴포넌트 종류의 같은 ID는 별개입니다.

| 필드 | 확장 | 프리셋 | 스텝 | 워크플로 |
| --- | --- | --- | --- | --- |
| `id` | 필수 | 필수 | 필수 | 필수 |
| `version` | 필수 | 필수 | 선택 | 필수 |
| `source` | 선택적 카탈로그 이름 | 선택적 카탈로그 이름 | 선택적 카탈로그 이름 | 선택적 카탈로그 이름 |
| `priority` | 선택. 기본값 `10` | 필수 정수, 최소 `1` | 사용 안 함 | 사용 안 함 |
| `strategy` | 사용 안 함 | 필수 | 사용 안 함 | 사용 안 함 |

명시적인 확장 우선순위도 최소 `1`이어야 합니다. 프리셋 전략은 `replace`,
`prepend`, `append`, `wrap`이며, 그 효과는
[프리셋 합성 계약](../presets/api.md)이 정의합니다.

`source`는 이길 것으로 기대하는 컴포넌트 카탈로그를 단언합니다. 더 낮은 우선순위의
카탈로그를 선택하거나, 탐색 전용 정책을 우회하거나, 직접 아티팩트 URL을 받거나,
번들 로컬 페이로드를 가리키지 않습니다. 명시적 소스는 이미 설치된 컴포넌트에
대해서도 확인되고, 네트워크 접근이 필요하며, 모호한 카탈로그 이름을 거부합니다.

`source`가 없으면 패키지된 확장과 프리셋이 각자의 카탈로그보다 우선합니다.
패키지된 워크플로도 사용될 수 있습니다. 안정 패키지 패치 호환성과 카탈로그 고정
적용은 CLI 레퍼런스가 설명합니다.

### 번들 참조

비어 있지 않은 `provides.bundles` 목록에는 스키마 `"1.1"`이 필요합니다. 비어
있거나 null인 목록은 참조가 없으며 스키마 `"1.0"`에서도 허용됩니다.

```yaml
provides:
  bundles:
    - id: qa-pack
      version: 2.0.0
      source: team-catalog
```

| 필드 | 요구 사항 |
| --- | --- |
| `id` | 필수인 안전한 슬러그. 이 매니페스트 안에서 고유하고 상위 ID와 달라야 함 |
| `version` | 필수인 정확한 SemVer |
| `source` | 이길 것으로 기대하는 선택적 번들 카탈로그 ID. URL이 아님 |

참조는 명령 실행 시 상위와 같은 유효 번들 카탈로그 스택을 통해 해석됩니다.
명시적 소스는 단언이지 우선순위 재정의가 아닙니다. 불일치하면 다른 카탈로그로
넘어가지 않고 실패합니다.

## 참조 확장

결과는 중첩된 설치가 아니라 하나의 평면 컴포넌트 계획입니다.

### 순서와 충돌 규칙

참조는 선언 순서대로 깊이 우선으로 순회되고, 이어서 선언하는 번들 자신의
컴포넌트가 옵니다. 최종 계획은 컴포넌트 그룹을 보존합니다. 확장, 프리셋, 스텝,
워크플로 순입니다.

각 컴포넌트는 `(kind, id)`당 최대 한 번 설치됩니다. 반복된 선언은 버전과 소스가
일치하면 합의된 것입니다. 생략된 소스와 명시적 소스는 다릅니다. 확장과 프리셋은
우선순위도, 프리셋은 전략도 일치해야 합니다. 생략된 확장 우선순위는 기본값인
`10`과 같습니다.

충돌하는 형제 참조는 선언하는 번들이 자신의 컴포넌트 선언으로 해결하지 않는 한
실패합니다. 모든 수준에서 번들 자신의 선언이 참조보다 우선하고, 자신의 선언
위치를 차지하며, 대체된 선언의 출처 체인과 함께 재정의 경고를 냅니다.

한 번들 ID는 하나의 확장 안에서 하나의 버전만 가질 수 있습니다. 두 번째 버전은 또
다른 설치가 아니라 오류입니다. 그 충돌을 해결하려면 호환되는 참조 릴리스를
선택하세요.

### 한계와 게이트

- 순환은 그 참조 체인과 함께 거부됩니다.
- 참조 중첩은 최대 `10`단계까지 허용됩니다.
- 루트를 제외하고 서로 다른 참조 번들 ID는 최대 `50`개까지 허용됩니다.
- 설치와 업데이트는 그래프의 모든 번들에 대해 Spec Kit 버전 요구 사항을
  강제합니다.
- 루트가 유일한 통합 게이트입니다. 참조된 번들의 통합 차이는 경고를 만듭니다.
- 도구와 MCP 요구 사항은 경고를 위해 그래프 전체에서 합쳐집니다.

`info`는 조회를 위해 탐색 전용 참조를 확장할 수 있습니다. 설치, 업데이트, 온라인
검증은 이를 설치 불가로 거부합니다. `validate --offline`은 참조를 확장하지 않으며
선언된 참조마다 한 번씩 경고합니다. `build`는 구조 검사만 수행합니다. 참조된
번들을 해석하지도 내장하지도 않습니다.

참조된 매니페스트는 네트워크 기반 카탈로그 다운로드가 필요합니다. 로컬/오프라인
참조 해석과 로컬 `bundle info` 미리 보기는 지원되지 않습니다.
퍼스트파티 번들 카탈로그는 릴리스 이력을 유지하지 않으므로, 퍼스트파티 참조는
카탈로그가 다음으로 넘어가면 사용할 수 없게 될 수 있습니다. 더 폭넓은 스키마
호환성 협상은 구현되어 있지 않습니다.

## 설치 기록과 소유권

프로젝트는 출처를 `.specify/bundle-records.json`에 저장합니다.

```json
{
  "schema_version": "1.0",
  "updated_at": "2026-01-01T00:00:00Z",
  "bundles": [
    {
      "bundle_id": "team-setup",
      "version": "1.0.0",
      "installed_at": "2026-01-01T00:00:00Z",
      "required_components": [
        {"kind": "extensions", "id": "bug", "version": "1.0.0"}
      ],
      "contributed_components": [
        {"kind": "extensions", "id": "bug", "version": "1.0.0"}
      ],
      "installed_versions": {
        "extensions:bug": "1.0.1"
      }
    }
  ]
}
```

| 기록 필드 | 의미 |
| --- | --- |
| `bundle_id`, `version` | 설치된 루트 번들의 정체성 |
| `installed_at` | 최초 설치 시각. 새로 고침/업데이트에 걸쳐 보존됨 |
| `required_components` | 독립적으로 제공된 컴포넌트를 포함해, 확장된 계획에서 필요한 모든 컴포넌트 |
| `contributed_components` | 번들에 귀속된 컴포넌트. 항상 요구 사항의 부분 집합 |
| `installed_versions` | 복수형 `kind:id`를 키로 하는, 알려진 실제 버전(선택). 요청된 고정과 구별됨 |
| `bundle_references` | 직접/전이 번들 참조의 선택적 목록. 각각 `id`, `version`, 해석된 카탈로그 `source`를 가짐 |

기록의 컴포넌트 항목은 복수형 `kind` 이름을 사용하고 `id`, `version`, 그리고
선언된 `source`, `priority`, `strategy`를 담습니다. 참조를 가진 번들의 경우 상위만
설치 기록을 갖습니다. 하위 참조는 한 번 기록될 뿐 별도의 번들 기록으로 설치되지
않습니다.

필요한 고정은 컴포넌트가 독립적으로 설치되었더라도 번들 간 충돌 검사에
참여합니다. 호환되는 독립 설치 컴포넌트는 번들에 의해 인수되거나, 새로
고쳐지거나, 제거되지 않습니다. 이미 다른 번들이 소유한 컴포넌트는 공유할 수
있습니다.

공유 요구 사항은 버전과 소스, 확장/프리셋 우선순위, 프리셋 전략에서 일치해야
합니다. 번들 업데이트는 다른 번들이 요구하는 고정을 교체할 수 없습니다. 번들을
제거하거나 새로 고침 중에 컴포넌트를 빼는 경우, 다른 번들이 여전히 필요로 하는
컴포넌트는 유지됩니다. 필요하면 소유권이 그것을 요구하는 남은 번들로 이전됩니다.

`required_components`가 없는 오래된 기록은 알려진 기여 고정을 유지합니다. 성공한
재설치/새로 고침은 전체 요구 사항을 기록합니다. 기록이 없으면 번들이 없는 것으로
취급되지만, 형식이 잘못된 기록과 호환되지 않는 스키마 메이저 버전은 빈 설치가
아니라 오류입니다.

기록 쓰기는 컴포넌트 작업이 성공한 뒤에 일어납니다. 그렇다고 설치, 업데이트, 새로
고침, 제거가 전역적으로 트랜잭션이 되는 것은 아닙니다. 실패와 롤백의 경계는 CLI
레퍼런스를 참고하세요.
