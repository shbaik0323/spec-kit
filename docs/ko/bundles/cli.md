# 번들 CLI 레퍼런스

`specify bundle` 명령 그룹은 번들을 탐색, 설치, 작성합니다.
명령 도움말은 `specify bundle <command> --help`를 사용하세요. 번들 카탈로그
명령에는 자체 중첩 도움말이 있습니다. `specify bundle catalog --help`.

## 프로젝트 요구 사항

| 명령 | 프로젝트 요구 사항 |
| --- | --- |
| `search`, `info` | 초기화된 프로젝트 없이 동작. 사용자 및 내장 카탈로그와, 해당하는 프로젝트 범위 설정을 사용 |
| `install`, `add`, `init` | 필요 시 프로젝트를 초기화 |
| `list`, `update`, `remove`, `catalog list/add/remove` | 초기화된 프로젝트 필요 |
| `validate`, `build` | 프로젝트를 초기화하지 않고 로컬 번들 소스에서 동작 |

`search`, `info`, `list`는 `--json`을 지원하고, 다른 bundle 명령은 지원하지
않습니다. 성공한 JSON 출력의 형태는 아래 각 명령에서 설명합니다. 모든 번들 실패가
JSON 봉투를 내보낸다고 가정하지 마세요. 일반적인 번들러 오류는 0이 아닌 종료
상태와 함께 오류로 보고됩니다.

## 사용 가능한 번들 검색

```bash
specify bundle search [query]
```

| 옵션 | 설명 |
| --- | --- |
| `--offline` | 네트워크에 접근하지 않음 |
| `--json` | JSON을 stdout으로 출력 |

모든 활성 카탈로그를 검색합니다. 선택적 쿼리는 이기는 항목의 ID, 이름, 역할, 태그,
설명의 부분 문자열과 일치합니다. 쿼리가 없으면 사용 가능한 모든 번들을 나열합니다.
각 ID는 최상위 우선순위 소스에서 한 번만 나타나며, 결과는 ID로 정렬됩니다.

텍스트 출력은 버전, 역할, 소스, 신뢰를 보여 줍니다. JSON은 `id`, `name`,
`version`, `role`, `description`, `source`, `install_policy`, `verified`, `trust`를
가진 항목의 배열입니다. trust는 verified로 표시된 항목이면 `verified`, 그렇지
않으면 `community`입니다. 이는 설치 정책을 바꾸지 않습니다.

## 번들 살펴보기

```bash
specify bundle info <bundle_id>
specify bundle info <bundle_id> --versions
```

| 옵션 | 설명 |
| --- | --- |
| `--offline` | 네트워크에 접근하지 않음 |
| `--json` | JSON을 stdout으로 출력 |
| `--versions` | 매니페스트를 다운로드하지 않고 현재 및 과거 카탈로그 버전 나열 |

`--versions`가 없으면 현재 매니페스트를 다운로드하고, 버전, 프리셋 우선순위와
전략, 통합, 소스 정책, 신뢰, 설치된 번들과의 참고용 중복을 포함해 완전히 확장된
컴포넌트 집합을 보여 줍니다. 필요한 컴포넌트가 이미 설치되어 있을 수 있습니다. 이
미리 보기는 모든 컴포넌트가 새로 추가된다거나 모든 설치 게이트를 통과했다는 약속이
아닙니다. `info`는 로컬 번들 경로를 지원하지 않습니다.

JSON에는 `id`, `name`, `version`, `role`, `description`, `author`, `license`,
`source`, `install_policy`, `provides`, `requires`, `verified`, `trust`,
`integration`, `components`, `overlaps`가 포함됩니다. 컴포넌트 항목에는 `kind`,
`id`, `version`, 그리고 선언된 `priority`나 `strategy`가 들어 있습니다.

참조가 있는 번들의 경우 JSON에는 다음도 포함됩니다.

- `references`: 참조된 각 번들의 `id`, `version`, 해석된 `source`,
  `install_policy`, `via`, `verified`, `trust`.
- 선언된 경우 컴포넌트의 `source`. 평면 번들은 이 필드를 생략합니다.
- 참조된 번들이 기여한 경우 컴포넌트의 `origin`. 가장 짧은 출처 체인을
  사용합니다.
- 선언을 대체하는 경우 컴포넌트의 `overrides`. 각 항목에는 대체된 `version`,
  `origin`, 그리고 `source`, `priority`, `strategy`가 있다면 그것이 들어 있습니다.
  선언한 서로 다른 번들이 각각 가장 짧은 경로로 표현됩니다. 재정의된 상위 선언은
  빈 origin을 갖습니다.

텍스트 출력에는 References 요약, 출처 체인, 재정의, 탐색 전용 알림이 포함됩니다.
참조된 번들은 자신의 신뢰 수준을 유지하며 상위 번들의 것을 상속하지 않습니다.

`--versions --json`은 대신 `id`, `versions`, `current`, `source`,
`install_policy`를 가진 객체를 내보냅니다. versions는 현재 릴리스를 맨 먼저, 이어서
과거 릴리스를 최신순으로 나열합니다.

매니페스트를 다운로드하거나 확장할 수 없으면 `info`는 검증된 확장 대신 카탈로그의
컴포넌트 수로 대체하지 않고 실패합니다.

<a id="install-a-bundle"></a>

## 번들 설치

```bash
specify bundle install <bundle_id-or-path>
specify bundle add <bundle_id-or-path>
```

`add`는 `install`과 같은 인자와 옵션을 받습니다.

| 옵션 | 설명 |
| --- | --- |
| `--integration <id>` | 초기화를 위한 통합을 선택하거나, 활성 통합을 판별할 수 없을 때 통합을 확인 |
| `--offline` | 네트워크에 접근하지 않음 |
| `--refresh` | 제공된 소스로부터 소유한 컴포넌트를 다시 적용 |
| `--version <version>` | 정확한 현재 또는 과거 카탈로그 릴리스 선택 |

인자는 카탈로그 ID, 로컬 번들 디렉터리, 매니페스트 파일, 또는 루트에
`bundle.yml`이 있는 빌드된 ZIP일 수 있습니다. 로컬 소스는 번들 참조를 선언하지
않는 한 번들 카탈로그를 거치지 않으며, 번들 참조는 카탈로그 스택을 통해
해석됩니다. 아카이브 URL은 직접 설치 인자가 아닙니다. 다운로드해 검증한 뒤 로컬
경로를 전달하거나 설치 허용 카탈로그를 사용하세요.

### 초기화와 통합

프로젝트가 없으면 설치는 먼저 매니페스트와 필수 호환성 게이트를 해석한 다음
프로젝트를 초기화합니다. 통합 선택은 명시적 옵션, 번들이 선언한 통합, CLI의 기본값
순으로 사용합니다.

기존 프로젝트에서는 기록된 활성 통합이 권위를 갖습니다. `--integration`은 그것을
전환하거나 번들 통합 불일치를 우회하지 않습니다. 통합이 고정된 번들에서
`.specify/integration.json`이 없거나 읽을 수 없어 프로젝트의 활성 통합을 판별할 수
없을 때는 `--integration`으로 대상을 확인하거나 프로젝트를 수리하세요.

통합에 중립적인 번들은 활성 통합을 상속합니다. 루트 번들이 통합 게이트입니다.
참조된 번들의 통합 대상이 다르거나 판별할 수 없으면 경고가 발생합니다.

### 재설치와 새로 고침

일반 설치는 호환되는 설치된 컴포넌트를 건너뛰고 그 로컬 편집을 보존합니다. 설치된
버전이 다르거나 알 수 없으면 아래의 패키지 패치 규칙을 제외하고는 고정을 충족할 수
없습니다. 독립적으로 설치된 컴포넌트는 절대 인수되거나 교체되지 않습니다.

일반 재설치는 로컬 매니페스트가 같은 번들 버전을 유지하더라도 기록된 번들 버전이나
소유한 컴포넌트 메타데이터의 변경(소유한 컴포넌트의 제거 포함)을 거부합니다.
변경되지 않은 컴포넌트의 순서를 바꾸거나 컴포넌트를 추가하는 데는 새로 고침이
필요하지 않습니다.

수정된 로컬 소스를 적용하려면 다음과 같이 합니다.

```bash
specify bundle install ./new-release/bundle.yml --refresh
```

새로 고침은 프리셋 우선순위 같은 프리미티브 수준 재정의를 보존하면서 번들이 소유한
컴포넌트를 각 프리미티브의 업데이트 경로를 통해 다시 적용합니다. 이 번들만이
소유한 버전 드리프트를 수리할 수 있습니다. 다른 번들이 여전히 필요로 하지 않는 한
생략된 소유 컴포넌트를 제거하고, 독립적으로 설치된 컴포넌트는 건드리지 않으며,
새로 고친 수와 제거한 수를 보고합니다.

공유 컴포넌트를 요구하는 모든 번들은 그 고정, 소스, 관련 설정에 합의해야 합니다.
고정되지 않은 새로 고침은 다른 번들이 고정으로 요구하는 버전을 교체할 수 없습니다.
새로 고침 없이 일치하는 설치 버전을 공유하는 것은 여전히 허용됩니다. 요구 사항
비교 규칙은 API 레퍼런스를 참고하세요.

번들 기록은 설치가 성공한 뒤에만 갱신됩니다. 컴포넌트가 실패하면 새로 설치된
컴포넌트는 최선의 노력으로 제거됩니다. 롤백 제거 오류는 무시되므로 디스크에 부분
상태가 남을 수 있습니다. 새로 고침 중에 수정되거나 제거된 기존 설치 컴포넌트는
복원되지 않습니다. 초기화도 롤백되지 않습니다.

### 패키지 패치 호환성

Spec Kit과 함께 제공되는 확장, 프리셋, 워크플로의 경우, 컴포넌트 `source`가
선언되지 않았다면 고정된 메이저/마이너 버전 안의 더 새로운 안정 패치가 경고와 함께
허용됩니다. 예를 들어 패키지된 `bug` 버전 `1.0.1`은 번들의 `1.0.0` 고정을 충족할
수 있습니다. 검증도 같은 경고를 사용합니다.

다운그레이드, 메이저/마이너 차이, 서로 다른 프리릴리스 버전은 이 예외에 해당하지
않습니다. 명시적 소스와 카탈로그로 해석된 릴리스는 정확한 고정 적용을 유지합니다.
패치 릴리스는 동작이 바뀌지 않았다는 보장이 아닙니다.

요청된 고정은 `required_components`와 `contributed_components`에 남습니다.
알려진 실제 버전은 `installed_versions` 아래에 별도로 기록되고
`bundle list --json`으로 표시됩니다.

### 정확한 카탈로그 릴리스

`--version`은 이기는 카탈로그가 공개한 번들 릴리스를 선택합니다. 그 릴리스 안의
컴포넌트 고정을 재정의하지는 않습니다. 비워 둘 수 없고, 로컬 소스와 함께 쓸 수
없으며, `--refresh`와 결합할 수 없습니다.

```bash
specify bundle install team-setup --version 1.1.0
```

없는 버전이 더 낮은 우선순위의 소스로 넘어가는 일은 없습니다.
탐색 전용 소스는 과거 릴리스를 포함해 설치할 수 없는 상태로 남습니다.
릴리스 이력 요구 사항은 카탈로그 레퍼런스를 참고하세요.

<a id="offline-limits"></a>

### 오프라인 한계

로컬 매니페스트, 디렉터리, ZIP은 `--offline`으로 패키지된 컴포넌트를 설치할 수
있습니다. 로컬 번들 자산은 컴포넌트 페이로드의 소스가 아닙니다. 카탈로그를 통해
해석되는 컴포넌트는 이미 설치되어 새로 고치는 경우에도 설치나 새로 고침에 네트워크
접근이 필요합니다.

카탈로그 번들 매니페스트와 참조된 번들 매니페스트는 네트워크 다운로드가
필요합니다. 로컬 루트는 오프라인 오류에서 해석되지 않은 첫 번째 번들 참조를 식별할
수 있습니다. 카탈로그 루트는 카탈로그나 루트 매니페스트를 가져오는 중에 더 일찍
실패할 수 있습니다. 패키지된 카탈로그 스냅샷은 탐색을 가능하게 할 뿐, 오프라인
카탈로그 ID 설치를 가능하게 하지 않습니다.

스텝 페이로드는 스텝 카탈로그를 통해서만 해석됩니다. 번들 로컬 `steps/<id>/`
디렉터리와 상대 스텝 `source` 값은 페이로드로 해석되지 않으므로, 스텝 디렉터리를
번들에 넣어도 오프라인으로 설치할 수 있게 되지는 않습니다.

## 번들 업데이트

```bash
specify bundle update <bundle_id>
specify bundle update --all
```

| 옵션 | 설명 |
| --- | --- |
| `--all` | 설치된 모든 번들 업데이트 |
| `--integration <id>` | 프로젝트의 활성 통합을 판별할 수 없을 때만 통합을 확인 |
| `--offline` | 네트워크에 접근하지 않음 |

설치된 번들과 설치 허용 소스가 필요합니다. 상위 번들의 현재 카탈로그 릴리스와
고정된 번들 참조를 다시 해석한 다음, `install --refresh`와 같은 라이프사이클 및
패치 호환성 규칙으로 소유한 컴포넌트를 새로 고칩니다. `update`는 과거의
`install --version` 선택을 유지하지 않습니다.

각 컴포넌트 고정은 이기는 카탈로그에서 정확한 릴리스를 선택합니다. 번들러는 예전
다운로드 URL을 추측하거나 더 낮은 우선순위의 카탈로그를 시도하지 않습니다.
버전을 공개하지 않는 레거시 확장 및 프리셋 항목은 고정을 강제하거나 아카이브의
버전을 검증할 수 없습니다. 그 고정을 강제할 수 있게 하려면 버전이 지정된 항목을
게시하세요. 고정되지 않은 스텝은 현재 카탈로그 릴리스를 선택합니다.

명시적인 `source`가 없으면 번들된 확장과 프리셋이 카탈로그 릴리스보다 우선합니다.
호환되지 않는 번들 고정은 일치하는 카탈로그 릴리스가 있더라도 거부됩니다. 번들된
워크플로는 호환되면 패키지된 버전을, 적절하고 온라인일 때는 카탈로그 릴리스를
사용합니다.

`--all`은 번들을 순차적으로 처리하고 실패 시 멈춥니다. 앞서 성공한 업데이트는
롤백되지 않습니다.

## 번들 제거

```bash
specify bundle remove <bundle_id>
```

다른 번들이 더는 필요로 하지 않는 기여 컴포넌트만 제거합니다.
남은 소유자가 없는 유지 컴포넌트는 이후 제거 시 정리될 수 있도록 그것을 요구하는
남은 번들로 소유권이 이전됩니다. 독립적으로 설치된 컴포넌트는 절대 인수되지
않습니다.

제거는 트랜잭션이 아닙니다. 컴포넌트 실패는 번들 기록이 변경되지 않은 채
부분적으로 제거된 프로젝트를 남길 수 있습니다. 명령은 실패와 복구 컨텍스트를
보고합니다.

## 설치된 번들 나열

```bash
specify bundle list
```

| 옵션 | 설명 |
| --- | --- |
| `--json` | JSON을 stdout으로 출력 |

설치된 번들 ID, 버전, 필요한 컴포넌트 수, 최초 설치 타임스탬프를 보여 줍니다.
수에는 독립적으로 제공된 컴포넌트가 포함됩니다.
JSON은 선택적인 `installed_versions`와 `bundle_references`를 포함해 API
레퍼런스의 기록 형태를 사용하는 설치 기록의 배열입니다.

## 번들로 프로젝트 초기화

```bash
specify bundle init [bundle_id]
```

| 옵션 | 설명 |
| --- | --- |
| `--integration <id>` | 초기화를 위한 통합 재정의 |
| `--offline` | 네트워크에 접근하지 않음 |

프로젝트가 존재하도록 한 다음 선택적으로 번들을 설치합니다. 변경 없는 설치를
반복하면 기존 컴포넌트를 건너뛰고 편집을 보존합니다. 새로 고침 규칙이 아니라 일반
설치 규칙을 따릅니다. 기록된 버전이나 소유 컴포넌트의 변경에는 `update` 또는
`install <path> --refresh`를 사용하세요.

## 번들 검증

```bash
specify bundle validate --path ./team-setup
```

| 옵션 | 설명 |
| --- | --- |
| `--path <path>` | 번들 디렉터리 또는 매니페스트. 기본값은 현재 디렉터리 |
| `--offline` | 네트워크 접근 없이 패키지된/설치된 컴포넌트에 대해 확인 |

매니페스트 구조와 컴포넌트 해석을 확인합니다. 온라인 검증은 번들 참조를 확장하고
확장된 계획 전반에서 순환, 버전, 소스, 충돌, 설치 정책을 확인합니다. 명시적인
컴포넌트 소스는 로컬 컴포넌트가 아니라 이기는 카탈로그에 대해 확인됩니다.

누락된 릴리스, 일치하지 않거나 모호한 소스, 탐색 전용 소스, 형식이 잘못된 카탈로그
메타데이터는 검증을 실패시킵니다. 접근할 수 없는 카탈로그를 포함해 검증할 수 없는
컴포넌트 참조는 경고를 만듭니다. 접근할 수 없는 더 높은 우선순위 카탈로그의 문제는
더 낮은 우선순위의 일치로 해결될 수 없습니다.
번들 참조 가져오기 실패는 온라인 검증을 실패시킵니다.

오프라인 검증은 선언된 번들 참조마다 확장되지 않았다는 경고를 한 번씩 냅니다.
경고가 있는 성공 결과는 전체 그래프를 설치할 수 있다는 증명이 아닙니다. 검증은
실행 중인 CLI를 `requires.speckit_version`에 비추어 확인하지 않습니다. 그 게이트는
install/update가 강제합니다.

## 번들 아티팩트 빌드

```bash
specify bundle build --path ./team-setup --output ./dist
```

| 옵션 | 설명 |
| --- | --- |
| `--path <directory>` | 번들 디렉터리. 기본값은 현재 디렉터리 |
| `--output <directory>` | 아티팩트 대상 위치. 기본값은 번들 디렉터리 |

매니페스트, README, 로컬 자산을 담은 `<id>-<version>.zip`을 만듭니다.
심볼릭 링크가 아닌 일반 `bundle.yml`과 `README.md` 파일, 그리고 구조적으로 유효한
매니페스트가 필요합니다. 빌드는 컴포넌트를 해석하거나 참조된 번들을 다운로드하지
않습니다. 온라인 검증을 대체하지 않습니다.

## 카탈로그 소스 관리

```bash
specify bundle catalog list
specify bundle catalog add <url>
specify bundle catalog remove <id-or-url>
```

`list`는 ID, URL, 우선순위, 범위, 정책과 함께 활성 스택을 출력합니다.
`add`와 `remove`는 프로젝트 범위 설정을 기록합니다.

| `catalog add` 옵션 | 설명 |
| --- | --- |
| `--policy <policy>` | `install-allowed`(기본값) 또는 `discovery-only` |
| `--priority <integer>` | 숫자가 낮을수록 우선순위가 높음. 기본값은 `10` |
| `--id <id>` | 명시적인 소스 ID. 없으면 URL이나 경로에서 도출 |

같은 소스를 일치하는 설정으로 다시 추가하면 아무 일도 일어나지 않고, 충돌하는
설정은 실패합니다. 내장 소스는 삭제할 수 없습니다. 내장 ID에 대한 프로젝트
재정의를 제거하면 더 낮은 범위의 소스가 복원됩니다.
