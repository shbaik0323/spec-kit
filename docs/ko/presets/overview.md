# 프리셋

프리셋은 Spec Kit 템플릿, 명령, 스크립트에 대한 쌓을 수 있고 우선순위로 정렬되는
사용자 정의입니다. 코어 파일을 포크하지 않고 조직 표준을 적용하거나, Spec Kit
프로세스를 여러분의 방법론에 맞추거나, 용어를 바꾸는 데 사용하세요. 확장은 기능을
추가하고, 프리셋은 기존 기능의 동작 방식을 바꿉니다.

> [!IMPORTANT]
> 서드파티 프리셋은 설치하기 전에 소스를 검증하세요. 커뮤니티 카탈로그는 탐색
> 채널이지 보안 보증이 아닙니다. 메인테이너는 카탈로그 항목의 완전성과 형식을
> 확인할 뿐, 커뮤니티 프리셋 코드를 검토, 감사, 보증, 지원하지 않습니다.

## 빠른 시작

`specify init`으로 초기화된 프로젝트 안에서 preset 명령을 실행하세요.

```bash
# 설치하지 않고 프리셋 탐색
specify preset search
specify preset info lean

# 번들된 프리셋 설치
specify preset add lean

# 설치된 프리셋과 템플릿 해석 확인
specify preset list
specify preset resolve spec-template

# 제거하고 남은 레이어 복원
specify preset remove lean
```

직접 작성했거나 검증한 프리셋이라면 `specify preset add --dev ./my-preset`으로
로컬 사본을, `specify preset add --from <archive-url>`로 고정된 릴리스 아카이브를
설치하세요. 로컬 설치는 소스를 복사합니다. 개발 디렉터리에 대한 실시간 링크가
아닙니다. 커뮤니티 검색 결과 자체가 ID 설치를 허용하지는 않습니다.

## 프리셋이 적용되는 방식

템플릿은 명세나 계획처럼 무엇이 만들어지는지를 정의합니다.
명령은 코딩 에이전트가 그것을 만들기 위해 따르는 지침을 담습니다.
스크립트는 실행 가능한 동작을 제공하며, 여러분이 설치하는 다른 코드와 같은 수준의
검토가 필요합니다.

각 논리적 파일 이름은 다음 레이어를 통해 독립적으로 해석됩니다.

| 우선순위 | 레이어 |
| --- | --- |
| 가장 높음 | `.specify/templates/overrides/`의 프로젝트 로컬 오버라이드 |
| 다음 | 활성화된 프리셋. 우선순위, 그다음 프리셋 ID 순으로 정렬 |
| 다음 | 활성화된 확장 기여. 우선순위, 그다음 확장 ID 순으로 정렬 |
| 가장 낮음 | Spec Kit 코어 기본값 |

우선순위 숫자가 낮을수록 우선합니다. 프리셋과 확장의 우선순위는 각자의 레이어
안에서 항목의 순서를 정합니다. 확장이 더 작은 숫자를 고른다고 프리셋 레이어보다
앞설 수는 없습니다.

템플릿과 스크립트는 필요할 때 해석됩니다. 명령은 설치와 조정 과정에서 활성 통합을
위한 명령 파일이나 스킬로 구체화됩니다. 에이전트가 호출할 때마다 스택을 해석하지는
않습니다. 기본 통합을 전환하면 그 통합에 대해 활성화된 프리셋이 다시
스캐폴딩됩니다. generic 통합은 프리셋의 명령 또는 스킬 오버라이드를 등록하지
않습니다.

설치된 프리셋이 없으면 나머지 프로젝트 오버라이드, 확장 기여, 코어 기본값이 계속
적용됩니다.

## 쌓기와 합성

검증한 여러 프리셋을 서로 다른 우선순위로 설치합니다.

```bash
specify preset add --dev ./team-base --priority 10
specify preset add --dev ./compliance --priority 5
specify preset set-priority compliance 3
```

두 프리셋 모두 기본 `replace` 전략으로 `spec-template`을 제공하면 `compliance`가
완전히 이깁니다. `team-base`만 제공하는 파일은 여전히 그 프리셋을 사용합니다.
우선순위가 같으면 프리셋 ID의 알파벳순으로 해결됩니다.

프리셋은 하위 레이어를 대체하는 대신 보강할 수 있습니다.

| 전략 | 효과 |
| --- | --- |
| `replace` | 이 레이어를 전부 사용하고 하위 레이어는 무시 |
| `prepend` | 이 레이어를 더 낮은 우선순위 콘텐츠 앞에 배치 |
| `append` | 이 레이어를 더 낮은 우선순위 콘텐츠 뒤에 배치 |
| `wrap` | 이 레이어의 자리 표시자 위치에 더 낮은 우선순위 콘텐츠를 삽입 |

템플릿과 명령은 네 가지 전략을 모두 지원합니다. 스크립트는 `replace`와 `wrap`만
지원합니다. 합성에는 하위의 `replace` 기반이 필요하며, 래퍼에는 알맞은 자리
표시자가 들어 있어야 합니다. 정확한 규칙은 API 레퍼런스가 정의합니다.

## 컨스티튜션 라이프사이클

초기화는 해석된 `constitution-template`으로부터 `.specify/memory/constitution.md`를
한 번 생성하며, 기존 컨스티튜션은 보존합니다. 이후의 `/speckit.constitution`
실행은 현재 합성된 템플릿을 해석하고, 프로젝트별 값과 개정에는 살아 있는
컨스티튜션을 사용합니다.

기본적으로 프리셋을 설치, 제거, 활성화, 비활성화하거나 우선순위를 바꿔도 살아 있는
컨스티튜션은 다시 쓰이지 않습니다. 번들된 `constitution-sync` 프리셋은 보호 장치가
있는 설치 시점 구체화와 명령 시점 전파에 참여합니다. 이 프리셋이 활성화된 동안에는
스택 변경이 변경되지 않은 생성 컨스티튜션을 새로 고칠 수 있지만, 직접 작성했거나
손으로 편집한 컨스티튜션은 보호됩니다. 이 프리셋을 설치하면 없는 컨스티튜션이
생성될 수도 있습니다.

## FAQ

### 어느 파일이 사용되고 있는지 어떻게 확인하나요?

템플릿은 `specify preset resolve spec-template`을, 명령은
`specify preset resolve speckit.specify`를 사용하세요. 합성된 출력에는 하나의 최종
소스 경로가 아니라 여러 기여 파일이 있을 수 있습니다.
숨겨진 레이어를 포함한 전체 아티팩트 스택은
`specify artifact info <name> --json`을 사용하세요.

### 비활성화는 제거와 같은가요?

아니요. 비활성화는 이후의 해석에서 프리셋을 제외하지만, 이전에 등록된 명령과
스킬은 그대로 둡니다. 전달된 오버라이드를 정리하고 남은 레이어를 복원해야 할 때는
제거를 사용하세요.

### 프리셋은 누가 지원하나요?

프리셋의 저장소를 통해 작성자에게 문의하세요. 커뮤니티 카탈로그에 포함되었다고
해서 유지 관리나 지원 책임이 Spec Kit 메인테이너에게 넘어오지는 않습니다.
