# 스펙 주도 개발 이해하기

스펙 주도 개발(Spec-Driven Development)은 전통적인 소프트웨어 개발의 **판을 뒤집습니다**. 수십 년 동안 코드가 왕이었고, 명세는 "진짜 작업"인 코딩이 시작되면 세웠다가 버리는 비계에 불과했습니다. 스펙 주도 개발은 이를 바꿉니다. **명세가 실행 가능해져서**, 구현을 안내하는 데 그치지 않고 동작하는 구현을 직접 생성합니다.

## 핵심 철학

스펙 주도 개발은 다음을 강조하는 구조화된 프로세스입니다.

- 명세가 "*어떻게*"보다 먼저 "*무엇을*"을 정의하는 **의도 주도 개발**
- 가드레일과 조직 원칙을 활용한 **풍부한 명세 작성**
- 프롬프트로 코드를 한 번에 생성하는 대신 **여러 단계에 걸친 정제**
- 명세 해석을 위한 고급 AI 모델 역량에 대한 **높은 의존**

Spec Kit은 요구사항이 바뀐 뒤 팀이 `spec.md`, `plan.md`, `tasks.md`를 어떻게
보존하거나 변경할지 규정하지 않습니다. 개념은
[명세 보존하기](persisting-specs.md)를, 기존 프로젝트의 발전 워크플로는
[기존 프로젝트에서 스펙 발전시키기](evolving-specs.md)를 참고하세요.

컴포넌트가 외부 소비자에게 인터페이스를 노출한다면
[계약 주도 개발](contract-driven-development.md)을 사용해, 각 측을 구현하기 전에
관찰 가능한 의무에 합의하세요. 이는 아키텍처나 저장소 구조와 무관하게 적용됩니다.

## 개발 단계

| 단계 | 초점 | 주요 활동 |
|-------|-------|----------------|
| **0에서 1로의 개발**("그린필드") | 처음부터 생성 | <ul><li>상위 수준 요구사항에서 시작</li><li>명세 생성</li><li>구현 단계 계획</li><li>프로덕션에 바로 쓸 수 있는 애플리케이션 빌드</li></ul> |
| **창의적 탐색** | 병렬 구현 | <ul><li>다양한 해결책 탐색</li><li>여러 기술 스택과 아키텍처 지원</li><li>UX 패턴 실험</li></ul> |
| **반복적 개선**("브라운필드") | 브라운필드 현대화 | <ul><li>기능을 반복적으로 추가</li><li>레거시 시스템 현대화</li><li>프로세스 조정</li></ul> |

## 실험 목표

우리의 연구와 실험은 다음에 초점을 둡니다.

### 기술 독립성

- 다양한 기술 스택으로 애플리케이션 만들기
- 스펙 주도 개발이 특정 기술, 프로그래밍 언어, 프레임워크에 묶이지 않는 프로세스라는 가설 검증

### 엔터프라이즈 제약

- 미션 크리티컬 애플리케이션 개발 시연
- 조직의 제약(클라우드 제공자, 기술 스택, 엔지니어링 실무) 반영
- 엔터프라이즈 디자인 시스템과 컴플라이언스 요구 사항 지원

### 사용자 중심 개발

- 서로 다른 사용자 집단과 선호에 맞는 애플리케이션 빌드
- 다양한 개발 접근 방식 지원(바이브 코딩부터 AI 네이티브 개발까지)

### 창의적이고 반복적인 프로세스

- 병렬 구현 탐색이라는 개념 검증
- 견고한 반복적 기능 개발 워크플로 제공
- 업그레이드와 현대화 작업을 다루도록 프로세스 확장
