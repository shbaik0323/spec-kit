# 복잡한 기능을 범위가 정해진 실행 단위로 구현하기

크거나 복잡한 기능은 `/speckit.specify`, `/speckit.plan`, `/speckit.tasks`까지는
순조롭게 진행되다가 구현 중에 품질이 떨어지는 경우가 많습니다. 긴
`/speckit.implement` 실행의 중간에 에이전트가 계획을 놓치거나, 태스크를 무시하거나,
환각을 일으키기 시작할 수 있습니다. 대개 컨텍스트 압축이 트리거되기 직전이나
직후입니다.

근본 원인은 컨텍스트 윈도 고갈입니다. 한 번의 구현 실행이 기능 전체를 컨텍스트에
담으려 하면 윈도가 차오르면서 모델의 품질이 떨어집니다. 해결책은 각 실행이
컨텍스트 한도 안에 넉넉히 머물도록 범위를 정하는 것입니다.

`/speckit.implement` 명령은 에이전트가 진행하기 전에 고려해야 하는 자유 형식
사용자 입력을 받습니다. 즉, 도구를 바꾸지 않고도 각 실행의 범위를 정할 수
있습니다.

## 방법 1: 호출당 실행할 태스크 수 제한

`/speckit.implement`가 모든 태스크를 한 번에 처리하게 두지 말고 일찍 멈추라고
지시하세요.

```text
/speckit.implement only execute tasks T001-T010, then stop and report progress
```

또는 단계(phase)로 범위를 정합니다.

```text
/speckit.implement only execute the Setup phase, then stop
```

완료된 태스크는 `tasks.md`에서 `[X]`로 표시되므로, 다음 `/speckit.implement`
호출은 멈춘 곳에서 이어서 진행합니다. 이렇게 하면 각 실행이 컨텍스트 한도 안에
넉넉히 머뭅니다.

## 방법 2: 에이전트에게 하위 에이전트 사용 지시

코딩 에이전트가 하위 에이전트를 지원한다면(예: GitHub Copilot CLI나 VS Code용
GitHub Copilot 확장), `/speckit.implement`에 개별 태스크를 위임하라고 지시할 수
있습니다.

```text
/speckit.implement delegate each parallel [P] task to a sub-agent
```

각 하위 에이전트는 기능 전체 컨텍스트가 아니라 집중된 컨텍스트, 즉 태스크 하나와
관련 계획 발췌를 받으므로 메인 세션에서 압축이 트리거되지 않습니다.

## 방법 3: 둘을 결합

매우 큰 기능에서는 범위 제한과 위임을 결합하세요.

```text
/speckit.implement execute only the Core phase, delegate [P] tasks to sub-agents
```

## 방법 4: 기능을 더 작은 스펙으로 분해

단계 하나만으로도 컨텍스트가 감당하지 못한다면, 기능을 독립적으로 명세된 하위
기능으로 나누세요. 각 하위 기능은 자체 `spec.md`, `plan.md`, `tasks.md`를 가지며
자체 specify/plan/tasks/implement 주기를 거칩니다.

이것이 "스펙의 스펙(spec of specs)" 접근 방식입니다. 첫 패스에서 거대한 기능을
모델에 과부하를 주지 않고 각각 구현할 수 있는 더 작고 자기 완결적인 스펙으로
나눕니다. 오버헤드가 가장 크므로 다른 방법으로는 다룰 수 없을 만큼 큰 기능에만
사용하세요.

전체 절차, 즉 로드맵 패스를 실행하는 방법, 로드맵 아티팩트를 구성하는 방법, 하위
스펙을 로드맵에 다시 연결하는 방법, 그리고 실제 예시는
[스펙의 스펙](spec-of-specs.md)을 참고하세요.

## 어떤 접근 방식을 고를까

| 접근 방식 | 적합한 경우 |
| --- | --- |
| N개 태스크 또는 한 단계로 제한 | 모든 에이전트. 가장 단순. 하위 에이전트 지원 불필요 |
| 하위 에이전트 위임 | 하위 에이전트를 지원하는 에이전트. 병렬성 극대화 |
| 범위 제한 + 위임 결합 | 하위 에이전트를 쓸 수 있는 에이전트에서의 큰 기능. 둘의 균형 |
| 더 작은 스펙으로 분해 | 단계 하나만으로도 컨텍스트가 감당하지 못할 때 |

대부분의 경우 실행당 태스크 범위를 제한하는 것이 가장 단순한 해결책입니다.
에이전트가 지원하고 병렬성을 원한다면 하위 에이전트 위임을 쓰고, 단계 하나가
여전히 한 번의 실행으로 다루기에 너무 클 때만 더 작은 스펙으로 분해하세요.
