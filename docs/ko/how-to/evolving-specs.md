# 기존 프로젝트에서 명세 발전시키기

요구사항이 바뀌거나 구현 중 발견한 사항 때문에 기존 기능을 수정해야 할 때 이
가이드를 사용하세요. 다음에 의도하는 계약을 명시적으로 만들고 그에 맞춰 전달하는
일을 다루며, 그 이후에 어떤 아티팩트를 남길지 선택하는 일은 다루지 않습니다.

저장소가 아직 Spec Kit으로 초기화되지 않았다면
[기존 프로젝트에 Spec Kit 도입하기](existing-projects.md)부터 시작하세요.

## 변경 평가하기

영향받는 동작을 식별하고, 사용 가능한 기능 아티팩트, 구현, 테스트, 유지 관리되는
설계 또는 제품 문서를 검토하세요. 합의된 의도에 대한 결함과 그 의도 자체에 대한
변경 제안을 구분하세요. 구현은 논의를 위한 근거이지, 요구사항을 대신하는 원천이
아닙니다.

발견한 사항이 의도된 동작, 구현 전략, 태스크 분해, 또는 코드만을 바꾸는지
판단하세요. 발견은 전달 도중을 포함해 스펙, 계획, 태스크 목록, 구현 어디에서든
나올 수 있습니다. 어디서 나왔는지가 어느 아티팩트가 권위를 갖는지를 결정하지는
않습니다.

## 수정된 의도를 명시적으로 만들기

모든 아티팩트 변경을 리뷰할 수 있도록 깨끗한 작업 트리나 전용 브랜치에서
시작하세요. 새 기능 디렉터리를 만들지, 남겨 둔 아티팩트를 수정할지는 팀이 선택한
보존 관례를 따르세요.
이전 기능 아티팩트가 퇴역했다면, 컨스티튜션만으로 기능이 명세된다고 가정하지 말고
유지 관리되는 요구사항과 결정 기록을 사용해 컨텍스트를 확립하세요.

1. 의도하는 계약을 `spec.md`에 작성합니다. `/speckit.specify`를 사용해 `specs/`
   아래에 새 기능 디렉터리를 만들거나 기존 스펙을 수정합니다.
2. `/speckit.plan`을 실행하거나 `plan.md`를 수정해 구현 접근 방식을 정의합니다.
3. `/speckit.tasks`를 실행하거나 `tasks.md`를 수정해 작업 분해를 도출합니다.
4. `/speckit.analyze`를 실행해 구현 전에 아티팩트 간 불일치를 보고받습니다.

코어에는 `spec.md`, `plan.md`, `tasks.md` 사이의 차이를 자동으로 조정하는 전용
명령이 없습니다. analyze는 아티팩트를 편집하지 않고 불일치를 보고합니다. 직접
조정하거나, 문서화된 동작에 따라 확장을 사용하세요. 파생 아티팩트를 교체하기 전에
중요한 구현 근거를 보존하세요.

팀이 의도를 바꾸는 발견을 받아들인다면 그 합의를 영향받는 아티팩트에 반영하세요.
태스크나 코드의 하위 수준 변경이 신뢰할 수 있어야 하는 스펙과 모순된 채로 남지
않게 하세요.

## 변경을 전달하고 평가하기

모든 보존 모델은 같은 전달/완전성 프로세스를 사용합니다.
specify -> plan -> tasks -> implement -> converge.

1. 명시적으로 의도한 아티팩트에 맞춰 `/speckit.implement`를 실행합니다.
2. 결과 구현과 아티팩트 diff를 검토합니다.
3. `/speckit.converge`를 실행해 컨스티튜션의 규율 아래 구현을 스펙, 계획, 태스크에
   비추어 평가합니다.
4. converge가 남은 누락에 대한 태스크를 추가하면, 합의한 기능이 완성될 때까지
   구현과 수렴을 반복합니다.

converge는 추가 전용입니다. 가능한 유일한 쓰기는 `tasks.md`에 남은 작업을 추가하는
것입니다. 코드를 문서화된 의도의 대체물로 받아들이도록 아티팩트를 다시 쓰지
않습니다. analyze도 converge도 보존 전략을 선택하지 않으며, 확장이 제공하는
조정 기능이 이 코어 명령들의 책임을 바꾸지 않습니다.

아티팩트를 수정하는 것만으로는 바뀐 동작이 전달되지 않습니다. 수정에 구현이
필요하다면 이 전달 루프를 완료하세요. 전달 후에는 팀의 보존 및 유지 관리 정책을
별도로 적용하세요.
