# 컴포넌트 간 계약을 정의하고 발전시키기

컴포넌트가 외부 소비자에게 인터페이스를 노출한다면, 그 소비자가 의존할 수 있는
계약을 정의하세요. **계약 주도 개발**이란 그 계약에 합의하고, 각 측을 계약에 맞춰
구현하고, 양측이 의무를 충족하는지 검증하는 것을 뜻합니다.

이는 스펙 주도 개발 안에 자리합니다. 제품 요구사항이 의도된 동작을 확립하고,
계약이 컴포넌트들이 그것을 전달하기 위해 어떻게 협력하는지 정의하고, 각 컴포넌트의
구현 계획이 내부 해결책을 설명합니다. 저장소 경계를 설계로 취급하지 말고 상호 작용
경계를 먼저 정의하세요.

이 가이드는 기존 Spec Kit 명령과 일반적인 버전 관리 아티팩트를 사용합니다.
자동 계약 동기화, 저장소 간 의존성 해석, 릴리스 오케스트레이션을 도입하지
않습니다.

## 언제 계약을 정의하는가

"외부"란 컴포넌트의 구현 경계 밖을 뜻하며, 반드시 그 프로세스, 저장소, 조직 밖을
뜻하지는 않습니다. 예는 다음과 같습니다.

- 백엔드 API를 호출하는 웹사이트.
- 다른 서비스를 호출하거나 그 이벤트를 소비하는 서비스.
- 라이브러리나 플러그인 인터페이스를 사용하는 애플리케이션.
- CLI를 호출하고 출력을 파싱하는 자동화.
- 합의된 형식으로 파일을 교환하는 컴포넌트.

이 원칙은 모놀리스, 모듈형 애플리케이션, 마이크로서비스, 그 밖의 아키텍처에
적용됩니다. 저장소 구조는 계약이 필요한지를 결정하지 않습니다. 계약의 형태와
상세함은 인터페이스에 맞아야 합니다. 작은 라이브러리에는 문서화된 시그니처와
동작이면 충분할 수 있고, 공개 HTTP API에는 OpenAPI 스키마와 실행 가능한 예제가
도움이 될 수 있습니다. 모든 계약에 별도의 스키마나 계약 레지스트리가 필요한 것은
아닙니다.

## 계약이 정의하는 것

각 측이 상대의 내부에 의존하지 않고 구현될 수 있게 하는 관찰 가능한 의무를
기술하세요.

- 형식과 검증 규칙을 포함한, 받아들이는 입력과 만들어 내는 출력.
- 오류 사례를 포함한 동작과 부수 효과.
- 멱등성, 이벤트 순서, 재시도, 타임아웃 같은 관련 상호 작용 보장.
- 호환성 기대치, 버전 관리, 지원 중단 정책.
- 제공자와 소비자를 위한 예제와 검증 기준.

스키마만으로는 합의 전체를 담지 못할 수 있습니다. 예를 들어 주문 요청의 형태는
그것을 재시도했을 때 두 번째 주문이 생길 수 있는지를 설명하지 않습니다. 그런
의미론도 문서화하세요. 내부 데이터베이스 구조나 구현상의 선택은 정말로 공개
인터페이스의 일부가 아닌 한 노출하지 마세요.

## 권위 있는 소유자는 하나

**한쪽이 권위 있는 계약을 소유하고, 다른 쪽이 그것을 소비합니다.** 보통
인터페이스를 노출하는 컴포넌트가 소유합니다. 인터페이스마다 소유권을 명시하고,
영향받는 소비자가 변경에 대한 합의에 참여하게 하세요. 소유권이 일방적인 변경을
뜻하지는 않습니다.

| 상황 | 계약을 공유하는 방법 |
|-----------|--------------------------|
| 양측이 같은 저장소에 있음 | 별도의 정의를 유지하지 말고 같은 권위 있는 파일이나 아티팩트를 참조하세요. 독립적으로 릴리스되는 컴포넌트는 그래도 자신이 지원하는 계약 버전을 기록해야 합니다. |
| 양측이 서로 다른 저장소에 있음 | 소비자가 고정할 수 있도록 버전이 지정된 계약 아티팩트/패키지를 게시하거나, 소비하는 각 저장소에 사본을 동기화하세요. |
| 소비자가 동기화된 사본을 유지함 | 권위 있는 원본과 정확한 버전 또는 커밋을 기록하세요. 사본은 읽기 전용 입력으로 취급하고, 변경은 원본에 제안하세요. |

벤더링한 사본의 경우, 옆에 둔 README에 원본 저장소, 원본 경로, 불변 리비전 또는
릴리스 아티팩트 다이제스트, 업데이트 절차를 기록할 수 있습니다. 패키지 의존성은
잠금 파일에 동등한 정보를 기록할 수 있습니다. 소비자에게 계약 아티팩트에 대한
인가된 접근을 제공하세요. 소비자가 제공자의 구현 저장소에 접근할 필요는 없습니다.

업데이트는 의도적으로 이루어집니다. 권위 있는 원본에서 변경에 합의하고, 버전을
게시한 다음, 각 소비자에서 버전 또는 사본 업데이트를 검토합니다. 모두를 조용히
"latest"로 동기화하지 마세요. 고정된 계약은 합의를 식별할 뿐, 배포된 제공자가
여전히 그것을 지원한다고 보장하지 않습니다.

## Spec Kit 워크플로 사용하기

1. **의도를 확립하고 인터페이스를 식별합니다.** `/speckit.specify`로 원하는 사용자
   동작을 담습니다. 각 상호 작용을 어느 컴포넌트가 제공하고 소비하는지
   식별합니다. 계약이 없다면 그것을 정의하는 것이 작업의 일부이지, 다른 곳에서
   이미 완료되어 있어야 하는 선행 조건이 아닙니다.
2. **의존하는 구현에 앞서 계약에 합의합니다.** `/speckit.plan` 중에 소유자가
   인터페이스 계약 초안을 작성하고 소비자와 함께 검토합니다. 어느 쪽이든 상대에
   대한 가정을 구현하기 전에 관찰 가능한 동작과 호환성 문제를 해소합니다. 그러면
   각 측은 합의된 버전에 맞춰 독립적으로 개발할 수 있습니다.
3. **영향받는 각 프로젝트에 합의를 제공합니다.** 에이전트에게 관련 제품
   요구사항과 함께 계약의 정확한 버전과 접근 가능한 내용을 제공합니다. 링크가
   있다고 해서 다른 저장소의 파일을 사용할 수 있다고 가정하지 마세요. 각
   프로젝트는 자체 로컬 `spec.md`, `plan.md`, `tasks.md`를 소유합니다. 다른
   프로젝트의 구현 계획을 복사하지 말고 계약을 참조하세요.
4. **검증을 명시적으로 계획합니다.** `/speckit.tasks`에 부정 사례를 포함한
   제공자 및 소비자 계약 테스트를 포함하도록 요청합니다. 데이터 형태뿐 아니라
   관찰 가능한 동작도 테스트합니다. 목(mock)을 상대로 한 소비자 테스트는 유용하지만
   실제 제공자가 계약을 준수하는지를 입증하지는 않습니다. 제공자 검증과 통합
   검증을 포함하세요.
5. **각 측을 구현하고 검증합니다.** 각 프로젝트에서 `/speckit.implement`를 사용한
   다음 합의된 검사를 실행합니다. 구현 중에 계약의 문제가 드러나면, 사본을 몰래
   바꾸지 말고 권위 있는 합의를 수정하고 영향받는 스펙, 계획, 테스트, 소비자
   버전을 조정합니다.
6. **호환되는 구현을 릴리스합니다.** 배포된 어느 컴포넌트 버전이 어느 계약 버전을
   지원하는지 추적합니다. 그 의존성을 중심으로 롤아웃과 롤백 순서를 정합니다.
   호환성을 깨는 변경의 경우, 소비자가 아직 사용하는 동작을 제거하기 전에
   마이그레이션과 중첩 기간에 합의합니다.

`/speckit.plan`은 외부 인터페이스가 관련될 때 이미 기능 범위의 `contracts/`
아티팩트를 만듭니다. 어느 아티팩트가 권위를 갖는지 명시적으로 선택하세요. 기능이
그곳에서 새 계약 초안을 작성할 수도 있고, 프로젝트의 다른 곳에 있는 확립된 계약에
대한 변경을 제안할 수도 있습니다. 승인된 원본과 버전을 기능 아티팩트에 기록하세요.
과거 스냅샷과 동기화된 사본은 편집 가능한 추가 진실 공급원이 아니며, Spec Kit은
이를 자동으로 게시하거나 동기화하지 않습니다.

변경 이후의 아티팩트 발전에 대해서는
[기존 프로젝트에서 스펙 발전시키기](evolving-specs.md)를 참고하세요.

## 실제 예시: 여러 서비스에 걸친 웹사이트 결제

웹사이트, 주문 서비스, 재고 서비스가 각각 자체 저장소에 있는 가상의 결제 기능을
생각해 봅시다. 아직 합의된 계약은 없습니다. 사용자 요구사항은 다음과 같습니다.
**고객은 품목을 예약할 수 있을 때만 주문할 수 있으며, 요청을 재시도해도 중복
주문이나 예약이 생겨서는 안 된다.**

먼저 두 계약을 식별하고 합의합니다. 아래는 요약입니다. 권위 있는 아티팩트는 위에서
설명한 입력/출력 세부 사항과 그 밖의 의무도 정의해야 합니다.

| 계약 | 소유자/제공자 | 소비자 | 관찰 가능한 합의 |
|----------|----------------|----------|----------------------|
| Orders API | 주문 서비스 | 웹사이트 | 멱등성 키와 함께 주문 요청을 받는다. 주문 또는 정의된 실패를 반환한다. 재시도가 중복 주문을 만들어서는 안 된다. |
| Inventory API | 재고 서비스 | 주문 서비스 | 요청된 모든 품목을 예약하거나, 부분 예약 없이 재고 부족을 보고한다. 재시도가 중복 예약을 만들어서는 안 된다. |

주문 서비스는 한 인터페이스에서는 제공자이고 다른 인터페이스에서는 소비자입니다.
Orders API 계약은 소유하지만 Inventory API 계약은 소유하지 않습니다.

패키지 대신 동기화된 사본을 사용하는 가능한 구조 하나는 다음과 같습니다.

```text
inventory-repo/
  .specify/
  contracts/inventory-api.yaml     # authoritative Inventory API contract
  specs/001-reserve-inventory/

orders-repo/
  .specify/
  contracts/orders-api.yaml        # authoritative Orders API contract
  contracts/inventory-api.yaml     # read-only copy pinned to Inventory API 1.0.0
  contracts/README.md              # source revision and sync procedure
  specs/001-place-order/

website-repo/
  .specify/
  contracts/orders-api.yaml        # read-only copy pinned to Orders API 1.0.0
  contracts/README.md              # source revision and sync procedure
  specs/001-checkout/
```

파일명과 버전은 예시이며 Spec Kit이 요구하는 구조가 아닙니다.
각 프로젝트는 독립적으로 초기화되고 평소의 SDD 워크플로를 사용합니다.

1. 재고 팀은 주문 팀과 Inventory API 1.0.0에 합의하고, 주문 팀은 웹사이트 팀과
   Orders API 1.0.0에 합의합니다. 각 소유자는 승인된 계약을 게시하고, 소비자는
   자신의 사본을 고정합니다.
2. 각 팀은 그 합의에 맞춰 결제에서 자신이 맡은 부분을 명세하고 계획합니다.
   웹사이트는 고객 상호 작용을, 주문은 주문 접수를, 재고는 예약 동작을
   기술합니다. 주문 측 계획은 두 계약 모두와, 예약과 주문 생성 사이의 실패를
   고려합니다.
3. 각 로컬 기능 스펙을 같은 제품 기능 이슈나 로드맵 항목에 연결하고, 계약 버전과
   관련된 제공자/소비자 스펙 또는 PR을 기록합니다. 로컬 기능 번호와 브랜치가
   일치할 필요는 없습니다. 이는 추적성이지 공유 구현 계획이 아닙니다.
4. 재시도, 재고 부족, 실패를 포함해 두 인터페이스를 구현하고 검증합니다. 각
   컴포넌트의 계약상 의무뿐 아니라 전체 결제 경로도 검증합니다.
5. 이번 최초 롤아웃에서는 의존하는 주문 구현을 활성화하기 전에 재고 구현을 사용
   가능하게 만든 다음 웹사이트 결제를 활성화합니다. 배포된 버전과 롤백 제약을
   기록합니다. 계약을 게시하는 것만으로는 그 구현을 사용할 수 있게 되지 않습니다.

나중에 Orders API 1.1.0이 선택적인 배송 메모를 추가한다면, 그 변경을
`orders-repo`에서 제안하고 검토하고, 기존 소비자와의 호환성을 검증한 다음,
웹사이트가 의도적으로 새 버전을 채택하게 하세요. 주문 서비스가 제공하기로 합의하지
않은 지원을 지어내려고 웹사이트의 동기화된 사본을 편집하지 마세요.

세 컴포넌트가 모두 한 저장소로 옮겨져도 같은 설계가 통합니다. 사본을 동기화하는
대신 권위 있는 계약을 직접 참조하세요. 프로젝트 구조와 명령 대상 지정은
[모노레포에서 Spec Kit 사용하기](monorepo.md)를 참고하세요. **계약이 구현들을
연결합니다. 저장소 구조는 그 합의를 공유하는 방식만 바꿉니다.**

## 예시: 컨트롤 플레인, 데이터 플레인, 통합 테스트

설정을 관리하는 컨트롤 플레인 프로젝트(`r1`), 트래픽을 처리하면서 설정을 적용하는
데이터 플레인 프로젝트(`r2`), 둘의 상호 작용을 검증하는 통합 테스트
프로젝트(`r3`)를 생각해 봅시다. 각각 자체 저장소에 있습니다. 이는 같은 원칙의 또
다른 적용이지, 시스템을 이런 식으로 구성해야 한다는 요구가 아닙니다.

### 상호 작용을 먼저 정의하기

컨트롤 플레인이 데이터 플레인에 설정을 적용해야 하는데 아직 계약이 없다고
합시다. 어느 쪽이든 상대에 대한 가정을 구현하기 전에 관찰 가능한 동작에
합의하세요.

| 계약 관심사 | 합의 예시 |
|------------------|-------------------|
| 입력 | 명시적인 검증 규칙을 갖춘 설정 리비전과 페이로드. |
| 출력 | 리비전을 식별하고 그것이 수락되었는지 적용되었는지 알리는 확인 응답. 적용이 비동기라면 호출자가 완료를 관찰하는 방법을 정의합니다. |
| 오류 | 유효하지 않은 설정과 오래된 리비전에 대한 정의된 응답. 이전의 유효한 설정은 활성 상태로 남습니다. |
| 동작 | 같은 리비전과 페이로드를 재시도해도 두 번 적용되지 않습니다. 다른 페이로드로 리비전을 재사용하면 거부됩니다. |
| 호환성 | 지원되는 계약 버전을 식별하고, 마이그레이션 중에 기존 호출자가 여전히 의존하는 동작을 보존합니다. |

이 예시에서는 `r2`가 인터페이스를 노출하고 권위 있는 계약을 소유합니다.
`r1` 팀은 계약에 대한 합의에 참여하고 고정된 버전을 소비합니다.
`r3` 팀은 같은 버전을 사용해 유효하지 않은 입력, 재시도, 지원되는 구현과의
호환성을 포함한 상호 작용을 검증합니다. 테스트는 합의에 대한 근거이지, 그것과
경쟁하는 정의가 아닙니다.

각 프로젝트는 자체 구현 또는 테스트 계획을 유지합니다. 우산 저장소, 일치하는
브랜치 이름, 세 저장소에 걸친 원자적 커밋을 요구하지 않고 공유 제품 의도와 계약
버전을 참조하세요.

### 합의된 계약을 의도적으로 발전시키기

아래 롤아웃 순서는 TongyiDai가 기여한 계약 발전 안내를 다듬은 것입니다. 최초의
상호 작용 계약이 이미 합의되어 사용 중이라고 가정합니다.

제공자와 소비자가 새로운 선택적 설정 필드를 추가하기로 합의했다고 합시다. 호환되는
채택을 명시적으로 계획하세요.

1. **호환되는 변경을 게시합니다.** `r2`의 권위 있는 계약을 갱신하고, 명시적인
   버전을 부여하고, 스키마와 호환성 픽스처를 게시합니다. 필드를 생략하면 기존
   동작이 보존되는지 검증합니다.
2. **사용을 활성화하기 전에 지원을 배포합니다.** `r1`이 `r2`의 새 동작을 필요로
   한다면, 먼저 `r2`를 이전 소비자와 새 소비자를 모두 지원하는 모드로
   배포합니다. 그런 다음에야 `r1`에서 의존하는 동작을 활성화합니다. 이 순서는
   저장소 이름이나 PR 병합 순서가 아니라 인터페이스 의존성을 따릅니다.
3. **버전을 인식하는 통합 테스트를 준비합니다.** 브랜치 이름이 아니라 지원되는
   계약 버전이나 명시적인 기능에 따라 기대치를 선택하도록 `r3` 커버리지를 일찍
   추가합니다. 기존 호환성 검사는 필수로 유지합니다. 호환되는 구현을 사용할 수
   있게 되면 기능을 활성화하기 전에 새 종단 간 게이트를 필수로 만드세요. 활성화
   후에 조용히 건너뛰지 마세요.
4. **불변 참조로 준비 상태를 추적합니다.** 기존 이슈나 로드맵이 승인된 계약,
   제공자 및 소비자 릴리스, 종단 간 결과, 이전 경로 제거 기준을 정확한 커밋이나
   릴리스 아티팩트에 연결할 수 있습니다. 병합된 변경과 배포되어 준비된 구현을
   구분하세요.
5. **롤백 경로를 보존합니다.** 이 제공자 우선 롤아웃에서는 제공자를 롤백하기 전에
   소비자의 새 동작을 비활성화하거나 롤백합니다. 영속 상태와 설정의 호환성도
   확인하세요. 배포 순서를 뒤집는 것만으로는 데이터 변경이 되돌려지지 않습니다.
   이전 계약은 지원되는 소비자가 더는 그것에 의존하지 않음을 확인한 뒤 이후의
   정리 작업에서만 제거하세요.

호환성을 깨는 변경을 피할 수 없다면, 마이그레이션이 가능하도록 지원을 넓히고,
소비자를 의도적으로 옮긴 다음에야 이전 동작을 퇴역시키세요. 버전이 지정된 계약을
게시하고 준비 상태를 기록한다고 해서 별개의 배포가 하나의 트랜잭션이 되지는
않습니다. 이들은 팀이 유지 관리하는 합의와 검사이지, 새로운 Spec Kit 의존성
해석기나 릴리스 오케스트레이터가 아닙니다.
